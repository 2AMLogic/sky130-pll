- **Methodology / criteria / limitations**:
  - Per-point criterion, part 1 (plumbing): ngspice exits 0, prints the harness's analysis-completion marker (`sim/harness: analysis complete`, echoed by the injected `.control` block -- ngspice does not print its own "Total analysis time" banner for a control-driven analysis), and emits no `Error:` line.
  - Per-point criterion, part 2 (measurement): the loop **locks** within the transient window. Lock criterion: mean output frequency over every sliding window of 5 output cycles stays within +/-2% of 3.90625 MHz through the end of the transient, with at least 5 cycles of in-band data after the lock instant. Time-to-lock is the earliest instant satisfying it. A point that never satisfies it is reported as **no lock** -- its final-window mean frequency is still shown, explicitly labelled as *not* a locked output frequency, so it can never be misread as one.
  - Measurement method: the harness injects the analysis itself (an ngspice `.control` block built by `sim/harness/measure.py`), `linearize`s `v(FBCLK)` onto the transient's own 40p grid and `wrdata`-dumps it; the reducer then extracts hysteresis-guarded, linearly-interpolated threshold crossings at 0.5*VDD (the threshold tracks each point's own swept supply, not the nominal rail) and derives frequency, duty cycle and time-to-lock from them. The dumps themselves are **not** committed -- `sim/README.md`'s retention policy treats waveform data as regenerable from the frozen netlist plus the logged environment.
  - Not measured here: loop bandwidth and phase margin are open-loop quantities and need their own AC/linearized-model testbench -- see `sim/harness/measure.py`'s module docstring for why they are deliberately out of this reducer's scope, and `sim/loop-ac/` for the campaign that does measure them.
  - DUT / limitations: this testbench's DUT is design/divider/divider_intN.sch driven open-loop (no VCO, PFD/charge pump or loop filter in the path) -- CLK is an ideal rail-to-rail pulse source (12.5 ps edges, 4 ns period = 250 MHz, 50% duty, the design's own lock target) instead of the real VCO's output, and NSEL[5:0]=111111 (N=64) is strapped statically via lab_pin ties to VDD/GND. RESETB is released by a pwl at 5-6 ns (design/divider/DESIGN.md's own issue #114 diagnostic method). `measure.lock`'s target_hz (3906250 Hz = f_CLK/N = 250 MHz/64) plus a 2% tolerance and a 5-output-period window/hold reproduces design/divider/DESIGN.md's own issue #114 pass criterion, applied via the harness's general-purpose sliding-window lock detector. `require_lock` is true. process_corners is the ratified rows 19/20 PVT grid (spec/target-spec.md, DR-003, #77) -- this manifest declares the same full 5-corner x 3-temp x 3-supply default grid every other sim/ manifest in this repo declares. **This record does not run that full 45-point grid.** N=64's 256 ns output period (versus N=25's ~22.7 ns or N=4's 16 ns) means the lock criterion's required window (11 output periods -- window_cycles + 1 + min_hold_cycles) costs a transient roughly an order of magnitude longer in absolute time, and this harness's standalone-divider cost was measured (while building this manifest) at close to a fixed ~0.89 s of wall-clock ngspice time per simulated nanosecond -- so a 45-point grid at this window length would cost on the order of 35 hours of ngspice wall-clock time, which issue #129's own PR could not absorb. This record instead covers a documented subset -- see the record's own Corner matrix run / subset-reason field -- and issue #130 tracks completing the full grid. This mirrors the precedent design/divider/DESIGN.md's 'Issue #114' section and sim/pll-lock's own early records already set for the identical problem (a full-grid run whose per-point cost made a single-PR full sweep impractical, deferred to a follow-up issue rather than forcing an unbounded compute bill on the PR that found the gap).
  - Analysis: transient, standalone divider (`tran 40p 3200n`, injected by sim/harness/measure.py from this manifest's own measure block -- see sim/divider-n64/testbench/tb_divider_n64.sch's header comment for why the schematic itself carries no .tran card). The 3.2 us window covers roughly 12.5 output periods at the target frequency (3.90625 MHz, 256 ns/period) after RESETB releases at 6 ns -- more than the 11 edges (window_cycles + 1 + min_hold_cycles) the lock criterion needs..
