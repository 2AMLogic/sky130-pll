WHY A FAMILY OF VARIANTS, AND WHAT EACH ONE IS FOR. The floor is not one number: it is a function of two ratios, and a single run would hide both. (1) The transition time divided by the grid step. When the clock's transition spans two or more grid samples, the two samples that bracket the 50% crossing both sit on the (straight) ramp and the linear interpolation in `measure.edge_times._interpolate_back` recovers the crossing exactly -- the floor collapses. When the transition is far shorter than one grid step, the bracketing pair straddles the entire edge, the interpolation is a guess, and the error is of order the grid step. (2) The period divided by the grid step. For a perfectly periodic clock the grid phase of successive edges walks by the FRACTIONAL part of that ratio, so the floor vanishes for a period that is an exact multiple of the grid step (every edge is quantized identically, so every measured period is identical) and is largest near a half-integer multiple. Both ratios are properties of the measurement, not of the design, which is exactly why they are measurable with no PLL transient at all. The variants: A1 = period 3.9952 ns (trial 2's 250.3 MHz), A2 = 3.9904 ns (trial 3's 250.6 MHz), A3 = 3.9170 ns (trial 5's 255.3 MHz), each at TR = TF = 20 ps -- one per locked draw of the Monte Carlo record, so that draw's measured figure can be restated against a floor taken at its own measured period; B = 3.9170 ns at TR = TF = 200 ps (exactly one grid step, the marginal case); C = 3.9170 ns at TR = TF = 1 ns (five grid steps, an edge the grid resolves). sim/pll-lock-mc/analysis/README.md tabulates which record each variant produced and restates the Monte Carlo record's three measured figures against them.

NO `measure.lock` BLOCK, deliberately: there is no loop here and nothing to lock, so the jitter population is the whole trace from `settle_from` = 0 (every one of the ~12,700 periods in the 50 us window) rather than a post-lock tail. That is the one respect in which this control's population differs from a Monte Carlo trial's, and it cuts the right way -- a larger population, so the reported floor is an estimate with tighter sampling error than the figures it is read against, not a noisier one.

`measure.jitter.gate_on_bound` IS FALSE, and `max_frac` is still row 9's ratified 1.0%: stating the bound is what makes this record's number directly comparable with the Monte Carlo record's, but gating on it would be meaningless here. A control whose job is to report how much jitter the pipeline invents for a jitter-free signal cannot sensibly FAIL for reporting a large number -- that IS the finding. (Note that `measure.py` does not gate a jitter bound on a manifest without a `lock` block in any case; `gate_on_bound: false` states the intent rather than relying on that.)

WHAT THIS CONTROL DOES NOT COVER, stated because a reader of a floor number is owed it. (a) It is a null control: the signal's true jitter is zero. A signal that really does jitter presents its edges at grid phases spread by its own jitter rather than at the deterministic walk a constant period produces, so the floor a jittering signal carries is a different (and, for edges the grid cannot resolve, larger) quantity than the one measured here -- see sim/harness/measure.py's 'The dump grid puts a floor under this figure' note, and issue #185 for the calibration control that would measure it. (b) It does not establish which of the variants above the real DUT is in: nothing committed in this repo states design/vco's CLK transition time at the row-9 operating point (issue #186), so the applicable floor cannot be read off this family without that measurement. (c) Its own sampling error is not zero: a floor estimated from N periods carries roughly 1/sqrt(2N) relative error, ~0.6% relative at N = 12,700 -- immaterial at the three-decimal figures reported, but it is an estimate, not an exact constant.

The PDK/corner machinery is exercised but inert: no device in the netlist uses the sky130 .lib section the harness patches, and an ideal pulse source has no temperature or process dependence, so the single (tt, 27 C, 1.80 V) point this manifest declares is the whole grid rather than a subset of a larger one -- widening it would mint duplicate points, not coverage. `supply_pattern` is null for the same reason sim/loop-ac's is: there is no supply terminal in this testbench to patch, and adding a decorative supply source so a regex has something to match would be worse. `supply_nominal` (1.80 V) is still load-bearing -- `measure.py` takes the comparison threshold as `threshold_frac * supply_v`, so it is what puts the threshold at 0.9 V, the exact 50% point of the pulse source's 0 -> 1.8 V swing.
