- **Methodology / criteria / limitations**:
  - Per-point criterion, part 1 (plumbing): ngspice exits 0, prints the harness's analysis-completion marker (`sim/harness: analysis complete`, echoed by the injected `.control` block -- ngspice does not print its own "Total analysis time" banner for a control-driven analysis), and emits no `Error:` line.
  - Per-point criterion, part 2 (measurement): the measured node `v(clk)` oscillates -- at least 4 rising crossings of 0.5*VDD after 60 ns of settling. A swept point that does not is reported as **no oscillation**, with no frequency attributed to it.
  - Measurement method: the harness injects the analysis itself (an ngspice `.control` block built by `sim/harness/measure.py`), `linearize`s `v(clk)` onto the transient's own 5p grid and `wrdata`-dumps it; the reducer then extracts hysteresis-guarded, linearly-interpolated threshold crossings at 0.5*VDD (the threshold tracks each point's own swept supply, not the nominal rail) and derives frequency, duty cycle and time-to-lock from them. The dumps themselves are **not** committed -- `sim/README.md`'s retention policy treats waveform data as regenerable from the frozen netlist plus the logged environment.
  - Transition time (reported, not gated on; issue #186): 10-90% transition time (rise/fall separately), each edge's duration between linearly interpolated crossings of 0.1*VDD and 0.9*VDD, from the same `v(clk)` samples the frequency/duty/jitter reduction above already extracted edges from -- rise and fall are reported separately (a single-ended current-starved ring's PMOS/NMOS tail legs are not assumed symmetric) as the mean over every edge that completes a monotonic crossing of both levels at or after the same population start instant (the lock instant, or `settle_from` when the manifest declares no lock criterion).
  - Not measured here: loop bandwidth and phase margin are open-loop quantities and need their own AC/linearized-model testbench -- see `sim/harness/measure.py`'s module docstring for why they are deliberately out of this reducer's scope, and `sim/loop-ac/` for the campaign that does measure them.
  - DUT / limitations: this testbench's DUT is design/vco/vco_ring5.sch driven open-loop (no PFD, charge pump, loop filter or divider in the path), exactly as sim/vco/testbench/tb_vco.sch's is -- it is that testbench's sibling, same DUT and open-loop harness, with VCTRL held at a single FIXED value (0.865 V, this manifest's own claim explains the basis) instead of swept, and a `measure.transition` block (issue #186's new extractor in sim/harness/measure.py, alongside `measure.duty_cycle`) added to the reduction. `measure.transition: true` requests the extractor's 10-90% default (TransitionSpec.frac_lo=0.1, frac_hi=0.9); sim/jitter-floor's own docstring also names 20-80% as an equally defensible convention, not used here because this manifest has no reason to prefer it over the more common figure. `tran_step` (5 ps) is fine enough to resolve an edge down to tens of ps with several grid samples per transition -- ~1/10 to ~1/40 of what a typical minimum-channel-length (0.15 um) sky130 core-device edge is expected to take -- so the reported figure is not itself limited by this manifest's own dump grid (the same 'resolve the edge, tran_step <= transition-time/2' condition sim/harness/measure.py's module docstring states); this is independent of, and finer than, sim/jitter-floor's/sim/pll-lock-mc's own 200 ps grid, which is what the resulting figure is read AGAINST, not run at. `tran_stop` (200 ns) with `settle_from` (60 ns, discarding ring startup, the same convention sim/vco/testbench/tb.json uses) leaves a 140 ns measured window -- about 35 cycles at the ~250 MHz this VCTRL targets, giving several dozen rise/fall transitions to average rather than one. `measure.ic` forces v(xxxvco.ring0)=0 with `uic` for the same reason sim/vco/testbench/tb.json does: a ring oscillator's DC operating point is the unstable all-stages-at-midrail equilibrium, and a noiseless simulator can sit on it indefinitely without a kick. Single PVT point (tt/125 C/1.80 V, `supply_tolerance` 0) by design, not a subset needing sim/README.md's override justification -- it is this manifest's own declared, whole grid: the claim is about ONE operating point (sim/pll-lock-mc's own base corner), not a PVT characterization, so widening the grid would answer a question this experiment does not ask (design/vco's transition time likely does vary some across corners, temperature and supply, which a future campaign could characterize the same way sim/vco/vco-supply-pushing did for frequency -- not attempted here, in scope).
