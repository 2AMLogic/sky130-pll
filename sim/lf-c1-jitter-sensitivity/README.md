# `sim/lf-c1-jitter-sensitivity/` — period jitter vs. the loop filter's `C1`

Sibling of `sim/lf-c2-jitter-sensitivity`: **byte-identical `measure` block**,
same DUT, same window and initial conditions, same sampling point and seed, same
reducer — a different degraded loop-filter component.

Here it is `C1`, the series capacitor of the `R1`/`C1` branch that forms the
loop's compensation zero. Per `design/loop-filter/DESIGN.md`'s own sizing
derivation, `C1` is the one component that sets *both* quantities the loop's
dynamics are stated over:

```
R1·C1 = tan(φm) / ωc                     [places the zero to hit φm at ωc]
C1    = Icp·Kv·sec(φm) / (2π·N·ωc²)      [sets |G(jωc)| = 1]
```

So shrinking `C1` raises the crossover (row 6) and collapses the phase margin
(row 7) together, leaving a badly under-damped loop whose residual phase error
rings. That is a degradation of the **loop's dynamics**, not of one filtering
path — which matters, because the filtering path was tried first and did not
work.

**Why this unit exists at all**: `sim/lf-c2-jitter-sensitivity` measured the
intuitive candidate — `C2`, the reference-ripple pole — and found it is **not a
lever** on this quantity (an 8.8× reduction bought 8 %). Read that unit's README
first; this one is the answer to its negative result.

Like its sibling, this is **not** a design claim and **not** ratified row 9's
evidence (`spec_rows` is empty). It exists to size T1 item 6's negative control
(`sim/pll-lock-mc-negative-control/`, issue #195), which needs a degradation
large enough that every control draw *misses* row 9's ratified 1.0 % bound and
small enough that every control draw still *locks*.

**No nominal arm of its own.** The comparison point is
[`sim/lf-c2-jitter-sensitivity`'s nominal-arm record](../lf-c2-jitter-sensitivity/records/20260926-084846-e572408.md)
— `design/top/top.sym` unmodified, **0.523 %** RMS — run from a byte-identical
`measure` block at the same seed and sampling point.
`sim/tests/test_negative_control_variant.py` asserts the two manifests still
agree, so that citation cannot quietly stop being valid, and the ~2 h a second
identical nominal run would cost buys nothing.

## The arms

Every arm's schematic is generated by `testbench/gen_c1_variant.py` from
`design/loop-filter/loop_filter.sch`, `design/top/top.sch` and
`sim/pll-lock-mc/testbench/tb_pll_lock_mc.sch` — one substitution each, `--check`
failing on a byte of drift, run in `npm run check:ci`. An arm named `c1div<F>`
has `C1`'s **area** divided by `F` (`W = L = 322/√F` µm).

## Results

**`C1` is a strong lever, and it runs into a lock cliff.** Four arms, one draw
each, read against the sibling unit's nominal **0.523 %**:

| --- | --- | --- | --- | --- | --- | --- | --- |

| `c1div9` | 23.19 pF | [`20260926-110626-044c894`](records/20260926-110626-044c894.md) | 347.4 ns | 249.9 MHz | **0.983 %** (4912 cyc) | ×1.88 | **no** — 1.7 % under |

1/1 trial PASS in each; `gate_on_bound` is false, so the `PASS` is the harness's
plumbing-plus-measurement criterion and not a statement about the bound. The
`c1div25` row is a genuine *no lock within 20 µs* and therefore carries **no**
jitter figure at all — that is the harness's own convention for a post-lock
quantity, and it is exactly the failure mode a negative control cannot afford.

**This is the sizing answer.** The degradation window for a control that must
both miss the bound *and* lock is **bracketed between `C1` area/9 and area/25**,
and two arms inside it satisfy both conditions:

- **`c1div12` is the chosen one** (`sim/pll-lock-mc-negative-control`'s DUT). It
  misses the bound by 27 % — enough that the nominal campaign's own draw-to-draw
  spread should not put any draw back under it: applying that campaign's measured
  spread (0.554–0.717 %, i.e. −13 % to +13 % about its mean) to 1.274 % gives
  1.11–1.44 %, all of it above 1.0 % — and it locks in **1.53 µs** from this
  unit's pre-charged start, so it has a large margin against the 50 µs cold-start
  window the control campaign runs in.
- **`c1div16` is the fallback if a `c1div12` draw ever comes in under the bound.**
  It has 8× the jitter margin but spends it on the other constraint: 13.13 µs to
  lock from a *pre-charged* start, against a cold-start campaign whose nominal
  draws already take 24.32–29.72 µs to reach lock in a 50 µs window. That is a
  real risk of censored no-lock draws, which cost the control exactly as much as
  a passing draw does.
- **`c1div9` is not usable**, and it is the reason this family needed four arms
  rather than one: at 0.983 % it sits 1.7 % *under* the bound, which would have
  produced a control that cannot fire.

**Read together with the sibling unit, the two families say something about the
design, not just about the control.** `C2` — the component whose stated job is
attenuating reference ripple — moves this figure by 8 % over an 8.8× change.
`C1` — the component that sets the crossover and the phase margin — moves it by
490 % over a 16× change, and past that the loop stops locking. So at this
operating point the measured period jitter tracks the **loop's damping**, not the
filter's ripple rejection. Nothing here changes a component value in `design/`,
and nothing here is a spec claim; what it does is put a measured number on which
loop-filter knob row 9 is actually sensitive to, which `design/loop-filter/DESIGN.md`
does not currently state and which `sim/loop-ripple` (#166) is the right place to
pursue.

**Two limitations, stated rather than left to be discovered.** (a) Every figure
here is **one draw at one seed**, at the pre-charged 20 µs window this unit uses
for affordability — not a population, and not the `DR-005` cold start row 9's
evidence is taken under. The ratios are what this unit produces; the control
campaign's own six cold-start draws are what actually decide whether the
degradation was sized correctly. (b) The lock times are this window's; a
cold-start lock time for a degraded arm is not measured anywhere, and the
`c1div16` concern above is therefore an argued risk rather than a measured one.

## Reproducing

```sh
python3 sim/lf-c1-jitter-sensitivity/testbench/gen_c1_variant.py --check

# one arm: point the manifest's `schematic` field at it, then run one draw
python3 - <<'EOF'
import json, pathlib
p = pathlib.Path("sim/lf-c1-jitter-sensitivity/testbench/tb.json")
m = json.loads(p.read_text()); m["schematic"] = "tb_lf_c1_jitter_c1div16.sch"
p.write_text(json.dumps(m, indent=2) + "\n")
EOF
python3 sim/run_corners.py lf-c1-jitter-sensitivity --mc
```

Arms run one at a time out of one testbench directory, exactly as
`sim/jitter-floor`, `sim/integrator-floor` and this unit's sibling do: each
record names the arm it drew and its own `corners/<record-id>/*.spice` pins the
netlist.
