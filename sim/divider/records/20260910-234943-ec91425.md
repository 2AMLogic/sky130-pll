- **Methodology / criteria / limitations**:
  - Per-point criterion, part 1 (plumbing): ngspice exits 0, prints the harness's analysis-completion marker (`sim/harness: analysis complete`, echoed by the injected `.control` block -- ngspice does not print its own "Total analysis time" banner for a control-driven analysis), and emits no `Error:` line.
  - Per-point criterion, part 2 (measurement): the loop **locks** within the transient window. Lock criterion: mean output frequency over every sliding window of 5 output cycles stays within +/-2% of 44.0044 MHz through the end of the transient, with at least 5 cycles of in-band data after the lock instant. Time-to-lock is the earliest instant satisfying it. A point that never satisfies it is reported as **no lock** -- its final-window mean frequency is still shown, explicitly labelled as *not* a locked output frequency, so it can never be misread as one.
  - Measurement method: the harness injects the analysis itself (an ngspice `.control` block built by `sim/harness/measure.py`), `linearize`s `v(FBCLK)` onto the transient's own 20p grid and `wrdata`-dumps it; the reducer then extracts hysteresis-guarded, linearly-interpolated threshold crossings at 0.5*VDD (the threshold tracks each point's own swept supply, not the nominal rail) and derives frequency, duty cycle and time-to-lock from them. The dumps themselves are **not** committed -- `sim/README.md`'s retention policy treats waveform data as regenerable from the frozen netlist plus the logged environment.
  - Not measured here: loop bandwidth and phase margin are open-loop quantities and need their own AC/linearized-model testbench -- see `sim/harness/measure.py`'s module docstring for why they are deliberately out of this reducer's scope, and `sim/loop-ac/` for the campaign that does measure them.
  - DUT / limitations: this testbench's DUT is design/divider/divider_intN.sch driven open-loop (no VCO, PFD/charge pump or loop filter in the path) -- CLK is an ideal rail-to-rail pulse source (12.5 ps edges, 909 ps period = ~1.10011 GHz, 50% duty) instead of the real VCO's output, and NSEL[5:0]=011000 (N=25) is strapped statically via lab_pin ties to VDD/GND, the same convention sim/pll-lock/testbench/tb_pll_lock.sch uses for design/top/top.sch's own NSEL bits. RESETB is released by a pwl at 5-6 ns (design/divider/DESIGN.md's own issue #114 diagnostic method). `measure.lock`'s target_hz (44004400 Hz = f_CLK/N = 1/909p/25) plus a 2% tolerance and a 5-output-period window/hold reproduces design/divider/DESIGN.md's own issue #114 pass criterion ('every steady-state inter-edge gap matches N/f_CLK to within 2%'), applied to FBCLK via the harness's general-purpose sliding-window lock detector instead of a bespoke script -- 'locked' here means 'the divider settled into clean, steady N:1 division and stayed there,' not a PLL frequency-lock claim (there is no loop). `require_lock` is true: unlike sim/pll-lock's closed-loop campaign, a standalone divider that fails to produce a clean N:1 division at this frequency, at this corner, is a genuine harness FAIL, not evidence of a coordination gap elsewhere in an unproven loop -- design/divider/DESIGN.md's own issue #114 measurements already predict every one of these 45 points should pass. process_corners is the ratified rows 19/20 PVT grid (spec/target-spec.md, DR-003, #77) -- the same 5-corner set every other sim/ manifest in this repo declares.
  - Analysis: transient, standalone divider (`tran 20p 300n`, injected by sim/harness/measure.py from this manifest's own measure block -- see sim/divider/testbench/tb_divider.sch's header comment for why the schematic itself carries no .tran card). The 300 ns window covers roughly 13 output periods at the target frequency (44.0044 MHz, ~22.7 ns/period) after RESETB releases at 6 ns -- comfortably more than the 11 edges (window_cycles + 1 + min_hold_cycles) the lock criterion needs. Bisecting the divider's own absolute maximum correct-division frequency (rather than checking a single fixed CLK frequency) stays an informal, uncommitted exercise -- sim/harness's own `sweep` mechanism alters a DC source's value (`alter <source> <value>`), not a pulse source's period, so a frequency-bisection campaign is out of this manifest's scope per issue #129; design/divider/DESIGN.md's 'Issue #114' section already carries that informal per-corner bisected-frequency table..
