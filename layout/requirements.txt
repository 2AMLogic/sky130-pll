# Pinned klayout-tools (`klt`) install for layout/'s DRC/LVS flow (issue #2).
#
# 2AMLogic/sky130-bandgap's own layout/requirements.txt (source commit
# f3b2b2e461938e323670498bcdbe9f4ec7de699b) pins an exact git commit rather
# than a PyPI version, because at the time it was written PyPI's
# `klayout-tools` release (v0.1.0) shipped only five verbs
# (`layers`/`stats`/`cells`/`drc`/`pdk`) -- this flow needs `gen`, `extract`
# and `lvs` too, which were `main`-only.
#
# That gap closed for a while: PyPI's `klayout-tools==0.2.0`
# (https://pypi.org/project/klayout-tools/0.2.0/) ships `gen`/`extract`/`lvs`,
# so this file pinned that plain PyPI version from issue #2 through issue #16.
#
# Bumped to a git-commit pin for issue #46 (2026-08-19) because PyPI had
# published nothing past `0.2.0` at that time and five of the eight `klt`
# gaps the PLL layout (#16) hit were fixed only on the tool's `main`. See
# `layout/klt-pin-decision.md` for that decision in full -- it is unchanged
# history, kept for context on why a git-commit pin was chosen once.
#
# Bumped again for issue #17 (2026-09-05), this time back to a plain PyPI
# version pin: `klayout-tools==0.4.0`
# (https://pypi.org/project/klayout-tools/0.4.0/, published 2026-09-05).
# `requirements.txt`'s prior header argued for a commit pin specifically
# because "there is no newer release" -- that premise is now stale. PyPI
# published `0.3.0` on 2026-08-22 and `0.4.0` on 2026-09-05 (release PR
# klayout-tools#1486), so the artifact-immutability / hash-checkable-wheel
# properties a version pin gives (and a commit pin does not) are available
# again without giving up anything the prior commit pin (`66f73d0`) picked
# up: `0.4.0`'s tag (`v0.4.0` -> commit `8a199cea7054b6a95144b0827f8484c9a7e0b52c`)
# is a descendant of both `66f73d0` (`gh api .../compare/66f73d0...v0.4.0`
# -> `ahead_by: 72, behind_by: 0`) and of klayout-tools#1201's DRC fix commit
# `bd5c7f43288c1ca372eb2e57116de26882d132c4` (`gh api
# .../compare/bd5c7f4...v0.4.0` -> `ahead_by: 258, behind_by: 0`), so this
# bump is a strict superset of the prior pin, not a partial rebase onto a
# different line of history.
#
# What #17's bump picks up, on top of everything #46 already picked up
# (restated in this file's git history for anyone diffing the header):
#
#   * 2AMLogic/klayout-tools#1201 -> merged via PR #1201, commit `bd5c7f4`.
#     `klt gen`'s minimum-gate-length MOS unit device no longer lets its
#     source/drain local-metal pads abut the gate -- they are now padded
#     clear of it. This is the fix for the exact defect this repo filed
#     generically as klayout-tools#1187 ("MOS unit device S/D local-metal
#     pads abut the gate at short l_um, tripping li1.space.1"), which is what
#     every one of the 52 `li1.space.1` violations in the PLL layout's prior
#     DRC record (`layout/pll/reports/20260821-080803-b0c10bd/drc.json`)
#     traced back to. See `layout/pll/reports/<record-id>/record.md` (the
#     record this bump produced) for whether the fresh DRC run at this pin
#     actually comes back clean of that rule class -- this header states what
#     the bump *picks up*, not what a re-run *proves*; those are checked
#     separately, per this repo's CLAUDE.md ("no claim without evidence").
#
# Bumped again for issue #157 (2026-09-23), staying on a plain PyPI version
# pin: `klayout-tools==0.6.0`
# (https://pypi.org/project/klayout-tools/0.6.0/, published 2026-09-22).
# The trigger was a reproducibility gap rather than a layout defect: the
# committed `klt erc` supply record (`layout/pll/erc-reports/`, issue #147)
# could not have been produced by this file's pinned build at all, because
# `0.4.0`'s `klt erc` has neither the `stackup[0].active_layer` field that
# `layout/pll/erc-supply-spec.json` requires nor the `provenance` block whose
# content hashes make a record re-verifiable. `layout/pll/erc-reports/README.md`
# said so in as many words. A pinned toolchain that cannot regenerate the
# repository's own evidence is not a pin.
#
# `0.6.0` is a strict superset of `0.4.0`, not a rebase onto a different line
# of history: `gh api .../compare/v0.4.0...v0.6.0` -> `ahead_by: 507,
# behind_by: 0` (and `v0.5.0...v0.6.0` -> `ahead_by: 271, behind_by: 0`).
# `0.5.0` was tagged 2026-09-15, which is before all three fixes below landed,
# so it is NOT a sufficient target -- `0.6.0` (tag `v0.6.0` -> commit
# `c622e8ad`) is the earliest published release that carries them.
#
# What #157's bump picks up, on top of everything #17 already picked up:
#
#   * 2AMLogic/klayout-tools#1979 -> fixed by PR #2001, merge commit
#     `cfec44c1` (merged 2026-09-17; `gh api .../compare/cfec44c1...v0.6.0`
#     -> `behind_by: 0`). `klt erc`'s antenna check counted tie-cell poly
#     resistors as gates, producing false antenna-ratio violations. The fix
#     adds `stackup[0].active_layer`, which makes the antenna denominator
#     `poly n diff` (real gate-oxide area) instead of raw poly area. This
#     repo's PLL layout draws poly resistors (`poly.res` 66/13 -- the
#     loop-filter and PFD/CP xhigh devices), which is exactly the
#     gate-oxide-free poly that field exists to exclude, and
#     `layout/pll/erc-supply-spec.json` already declares it.
#   * 2AMLogic/klayout-tools#1968 -> fixed by PR #1984, merge commit
#     `f59e869f` (merged 2026-09-17; `behind_by: 0` vs `v0.6.0`). `klt erc`
#     emitted no `status` and no `provenance` block, so its output could not
#     be graded.
#   * 2AMLogic/klayout-tools#2036 -> fixed by PR #2049, merge commit
#     `471dc9f8` (merged 2026-09-18; `behind_by: 0` vs `v0.6.0`). `klt erc`'s
#     `provenance` block gained the `content_hash` entries that pin a report
#     to both of its inputs (the layout AND the spec), which is what makes a
#     committed record re-verifiable rather than merely present.
#
# As with #17's header: this states what the bump *picks up*, not what a
# re-run *proves*. What the re-runs actually produced is in the refreshed
# records under `layout/trivial-cell/reports/`, `layout/pll/reports/` and
# `layout/pll/erc-reports/` -- read those, not this comment, for the verdict.
#
# Bump discipline, mirrored from sky130-bandgap and from #46's own commit-pin
# precedent (still the discipline to follow if a future bump goes back to a
# git-commit pin instead of a PyPI version): pin explicitly (a commit hash or
# an exact version, never floating `main` or an unpinned release); state in
# this header what the bump picks up and what it changes; and re-run BOTH
# layout/bin/run-trivial-cell-flow.sh and layout/bin/run-pll-layout-flow.sh,
# checking the refreshed records in, as the non-regression proof.
#
# `klt --version` reports `0.6.0` at this pin (upstream has bumped the package
# version on every release since `0.3.0`, unlike the #46 commit-pin era where
# `klt --version` stayed at `0.2.0` across different commits) -- but
# `layout/bin/setup-venv.sh` still installs with `--force-reinstall`
# unconditionally, which remains correct and is not a no-op to remove: it is
# what makes a future pin bump that reuses the same reported version (e.g. a
# later commit pin) safe again without a separate code change.
klayout-tools==0.6.0
